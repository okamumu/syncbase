# 汎用データ同期・履歴管理フレームワーク 仕様書（案）

**Version:** 0.1  
**Status:** 基本設計案  
**初期適用先:** 学会・大会データ管理システム  
**想定実装:** Python + SQLite（将来的にPostgreSQL対応可能）

---

## 1. 目的

### 1.1 背景

学会・大会運営では、講演申込、参加登録、委員情報などが複数の外部システムから提供される。

これらのデータは、そのまま利用されるわけではなく、以下の処理を伴う。

- 氏名・所属などの名寄せ
- 申込情報の修正
- 複数入力元のデータ統合
- マスターDB上での直接編集
- 外部ツール向けCSVの生成
- データ更新・出力履歴の確認

単純なCSVの上書き取り込みでは、DB上で行った修正が失われる可能性がある。

また、取り込みや出力を繰り返す際に、何が変更されたのか、どのデータを外部へ出力したのかを把握する仕組みが必要である。

### 1.2 設計目標

本フレームワークでは、以下を実現する。

1. 外部データとマスターDBの変更を独立して管理する。
2. 前回同期時点からの変更を検出する。
3. 競合する変更を検出し、人間が解決できるようにする。
4. 複数の入力元から同一対象への情報を統合する。
5. 入力元の原データを保持し、統合後のマスターデータと区別する。
6. DBの変更履歴を保存し、過去の状態を参照できるようにする。
7. CSV出力についても差分・出力履歴を管理する。
8. 特定の業務やマスター構造に依存しない汎用的な機構とする。

### 1.3 基本思想

Doltのバージョン管理とMDMのGolden Record管理を組み合わせる。

**Dolt型の機能**

- Snapshot
- Commit
- Diff
- Three-way Merge
- Conflict Detection
- Version History

**MDM型の機能**

- Source Record
- Entity Resolution
- Record Linking
- Golden Record
- Data Provenance
- Human Override

これらを、既存のRDBを利用した軽量なフレームワークとして実現する。

Doltと完全互換のGit操作やSQL構文の実装は目標としない。

## 2. システムの基本構造

### 2.1 アーキテクチャ

システムを以下の3層に分離する。

**第1層：Input / Output Adapters**

外部データと内部データモデルとの変換を担当する。

- CSV
- Jotformなどのフォームサービス
- API
- 手入力
- 外部ツール向けCSV出力

**第2層：Data Management Core**

業務に依存しない共通機能を提供する。

- Versioning：スナップショット、変更履歴
- Diff Engine：データ比較
- Merge Engine：3者マージ
- Reconciliation：レコードの照合・統合
- Provenance：データの由来管理
- Validation：データ整合性検証
- Export History：出力履歴管理

**第3層：Master Database**

業務固有のデータを保持する。

初期適用先では、以下が対象となる。

- 人
- メールアドレス
- 講演
- 著者
- 参加登録
- 委員
- その他の大会運営データ

共通コアは、これらの具体的なマスター名称を知らなくても動作することを原則とする。

### 2.2 マスターの定義

各マスターは、設定によって次の情報を定義する。

| 項目 | 内容 |
|---|---|
| Entity Type | マスターの種類 |
| Primary Key | 一意識別子 |
| Fields | 管理する項目 |
| Relationships | 他マスターとの関係 |
| Constraints | 整合性条件 |
| Match Rules | 同一レコードの判定方法 |
| Merge Rules | 項目の統合方法 |

マスターの構造は既存のリレーショナルテーブルを利用できることとし、すべての業務データを汎用的なKey-Valueテーブルへ移行することは要求しない。

## 3. データの管理モデル

### 3.1 データの種類

データを次の4種類に分離する。

**Source Data**

外部入力元から取得した原データ。

- 入力元ごとに管理する。
- 元の値を保持する。
- 再取り込みによって過去の原データが消失しないようにする。
- マスターの修正を原データへ無条件に反映しない。

**Master Data**

名寄せ・統合・人手による修正が適用された、業務で使用する正本。

**Synchronization State**

入力元とマスターの間で、最後に同期・照合した際の基準状態。

**Version / Export History**

マスターの更新履歴、過去のスナップショット、外部出力の記録。

### 3.2 識別子

各レコードには以下を区別して保持する。

- `source_id`：入力系統
- `external_key`：入力元でのレコード識別子
- `entity_type`：マスターの種類
- `entity_id`：マスター内の識別子

同じマスターに複数の入力元が結びつくことを許可する。

また、1件のフォーム回答から講演1件と著者複数件が作成される場合など、入力レコードとマスターの対応は必ずしも1対1とはしない。

### 3.3 データの由来

可能な範囲で、マスターの各項目について以下を記録できることとする。

- 採用された値
- 値の入力元
- 採用日時
- 自動採用か手動採用か
- 手動で採用した場合の判断情報

これにより、マスターの値と元の申込情報が異なる場合でも、その理由を追跡できるようにする。

---

## 4. スナップショット・バージョン管理

### 4.1 スナップショット

外部入力の同期について、最低限以下の2つの基準を保持する。

1. 前回同期時の入力元データ
2. 前回同期・照合時のマスターデータ

これらは入力系統および対応レコードごとに管理する。

マスター全体を毎回複製する実装は必須ではなく、必要な項目のスナップショットやマスターのバージョンを参照する方式でもよい。

### 4.2 コミット

マスターへの更新は論理的な操作単位でコミットする。

コミットには次のメタデータを持たせる。

- Commit ID
- 日時
- 操作主体（ユーザーまたはシステム）
- 操作種別
- 入力元またはバッチID
- 変更内容
- 変更理由（任意）
- 親バージョン

関連する複数マスターの変更は、原則として1つのトランザクションで適用する。

### 4.3 履歴参照

以下の操作を提供する。

- 任意の2バージョン間の差分表示
- 変更レコードと変更項目の表示
- 変更者・変更日時・入力元の追跡
- 過去バージョンの参照
- 指定変更の取り消し

取り消しは、現在の他の変更を破壊しないよう、原則として逆方向の変更を新たなコミットとして適用する。

DB全体の完全復元は別機能として扱う。

### 4.4 スナップショット更新タイミング

入力元の観測状態とマスター側の同期基準は、区別して更新する。

- 入力元の新しいデータを正式に受理した場合、入力元の観測履歴を更新する。
- マスター側の同期基準は、対応する変更が同期・照合された時点で更新する。
- マスターへの直接編集だけを理由に、入力系統側の同期基準を無条件に更新しない。
- 明示的に解決した不一致の判断情報は保持する。

これにより、未解決の変更が、単なる再取り込みによって見えなくなることを防ぐ。

## 5. 差分検出・3者マージ

### 5.1 比較単位

差分比較は原則として次の単位で行う。

`Entity Type / Entity ID / Field`

ただし、配列、繰り返し項目、関連レコードについては専用の比較ルールを設定できることとする。

### 5.2 入力元とDBの比較

各入力系統について、以下の4つの値を利用する。

| 記号 | 意味 |
|---|---|
| S0 | 前回同期時の入力元の値 |
| S1 | 今回取得した入力元の値 |
| M0 | 前回同期・照合時のマスターの値 |
| M1 | 現在のマスターの値 |

**S0とM0は一致するとは限らない。**

これは、名寄せや手動修正によって、入力元の記載とマスターの正本が異なる場合があるためである。

### 5.3 基本判定

| 入力元の変更 | マスターの変更 | 基本処理 |
|---|---|---|
| なし | なし | 変更なし |
| なし | あり | マスターの変更を維持 |
| あり | なし | 入力元の更新候補 |
| あり | あり・結果が一致 | 一致として処理 |
| あり | あり・結果が不一致 | コンフリクト |

入力元の更新候補については、マージルールによって自動採用または確認待ちとする。

特に、過去の名寄せ・手動判断によって入力元とマスターの値が意図的に異なる場合、単純に入力元を優先してはならない。

### 5.4 コンフリクト

コンフリクトには以下を含める。

- 同一項目の異なる変更
- レコードの削除と変更の競合
- 同一対象に対する複数入力元の競合
- 外部データと名寄せ結果の競合
- マスター間の関係に関する競合

コンフリクト解決時には、少なくとも以下を選択可能とする。

- 入力元の値を採用
- マスターの値を維持
- 手動で別の値を指定
- 保留

解決判断は履歴に保存する。

### 5.5 手動修正の保護

手動で確定したマスター値を、新しい入力データによって無条件に上書きしない。

項目ごとに、必要に応じて以下のポリシーを設定できることとする。

- 自動更新可能
- 入力元優先
- マスター優先
- 手動承認必須
- 手動確定値の保護

これにより、文字列としての変更検出と、業務上どの値を採用するかの判断を分離する。

### 5.6 レコードの追加・削除

以下を区別する。

- 外部入力元に新規追加されたレコード
- 外部入力元から削除されたレコード
- DBに直接追加されたレコード
- 別入力系統から追加されたレコード

ある入力元に存在しないことだけを理由に、マスターから削除しない。

また、全件スナップショット形式の入力と、差分更新形式の入力を区別する。

全件入力からレコードが消えた場合の取消・削除処理は、入力系統ごとのルールで定義する。

### 5.7 欠損値の扱い

次の状態を明確に区別する。

- 項目が提供されていない
- 空文字列が明示されている
- NULLが指定されている
- 値の削除が指示されている

特に差分入力では、項目の欠落を削除と解釈しない。

## 6. 名寄せ・マスター統合

### 6.1 基本方針

外部入力元のレコードとマスターの対応付けを、値の更新とは独立して管理する。

名寄せには以下の処理を含める。

- 同一対象の候補抽出
- 複数候補の比較
- 同一対象として結び付ける
- 別対象として新規作成する
- 誤った結び付けを解除する
- マスターを統合する
- 統合済みマスターを必要に応じて分離する

### 6.2 マスターの種類

名寄せ対象は「人」に限定しない。

例：

- 同一人物
- 同一講演
- 同一参加登録
- 同一団体
- 同一所属先

具体的な照合方法は、マスター種別ごとに設定する。

### 6.3 属性の採用

複数の入力元が同じ属性に異なる値を提供する場合、統合ルールまたは人間の判断によりマスター値を確定する。

単純な入力元優先順位だけでなく、手動確定値を維持するルールも必要とする。

### 6.4 対応関係の履歴

名寄せによって外部レコードとマスターの対応先が変化した場合も、その変更を記録する。

対応先を変更する操作と、氏名などの属性値を変更する操作は区別する。

## 7. CSV出力・出力履歴

### 7.1 基本方針

外部ツール向けCSV出力は一方向とする。

出力したCSVを再びDBへ取り込むことは前提としない。

したがって出力では3者マージを行わず、前回出力と今回出力の2者比較を利用する。

### 7.2 出力定義

CSVの種類ごとにExport Profileを定義する。

- Profile ID
- 出力対象マスター
- 対象抽出条件
- 出力項目
- 出力項目の変換ルール
- レコード識別キー
- 並び順
- 文字コード
- CSV形式

### 7.3 差分検出

今回生成したCSVと、同じ出力定義に基づく前回の正式出力を比較する。

検出対象は以下とする。

- 追加行
- 削除行
- 変更行
- 変更項目

比較は原則として行の識別キーに基づき行う。

行順の変更だけをデータ変更とみなすかは、Export Profileで設定する。

### 7.4 出力履歴

出力ごとに、以下を記録する。

- Export ID
- Export Profile
- 出力日時
- 出力者
- 元となったDBバージョン
- 出力件数
- 出力内容のスナップショット
- ファイルのハッシュ値
- ファイル名
- 前回出力との差分

必要に応じて、生成したCSVファイル自体を保存する。

### 7.5 出力時の操作

1. 現在のDBからCSV候補を生成する。
2. 前回の正式出力との差分を計算する。
3. 差分をプレビューする。
4. ユーザーが出力を確定する。
5. CSVを生成・保存する。
6. 正常完了後、出力履歴を記録する。

プレビューだけでは出力履歴の基準を更新しない。

同じ内容を再出力した場合も、出力実行履歴としては記録可能とする。

### 7.6 過去の出力

ユーザーは以下を実行できる。

- 過去の出力一覧を表示
- 過去のCSVを取得
- 任意の2回の出力を比較
- 変更された項目を確認
- 過去の出力時点のDBバージョンを確認

ファイルそのものの保存期間については別途設定可能とする。

## 8. 汎用API

### 8.1 入力

- `stage(source, records, mapping)`
- `preview(batch_id)`
- `diff(batch_id)`
- `conflicts(batch_id)`
- `resolve(batch_id, decisions)`
- `commit(batch_id)`

### 8.2 履歴

- `history(entity_type, entity_id)`
- `get_version(commit_id)`
- `compare_versions(v1, v2)`
- `revert(commit_id)`

### 8.3 名寄せ

- `match_candidates(source_record)`
- `link(source_record, entity_id)`
- `unlink(source_record)`
- `merge_entities(entity_ids)`
- `split_entity(entity_id, rule)`

### 8.4 出力

- `prepare_export(profile)`
- `export_diff(export_id)`
- `confirm_export(export_id)`
- `export_history(profile)`
- `compare_exports(export_id_1, export_id_2)`

API名称は仮称であり、実装時に整理する。

## 9. 論理データモデル

最低限、以下の管理情報を用意する。

| 管理対象 | 役割 |
|---|---|
| `sources` | 入力系統の定義 |
| `source_records` | 入力元のレコードと観測履歴 |
| `entity_links` | 外部レコードとマスターの対応 |
| `sync_states` | 前回同期の基準状態 |
| `commits` | マスター更新の単位 |
| `changes` | 項目・レコード単位の変更履歴 |
| `conflicts` | 競合と解決結果 |
| `field_decisions` | 手動確定値や採用ルール |
| `export_profiles` | CSV出力定義 |
| `export_runs` | CSV出力実行履歴 |
| `export_records` | 出力内容のスナップショット |

これらは論理的な構成要素であり、必ずしも各要素に対して物理テーブルを1つずつ設けることを意味しない。

既存の業務マスターテーブルと管理用テーブルは分離する。

## 10. UI要件

### 10.1 入力プレビュー

取り込み前に次の分類を表示する。

- 新規追加
- 入力元だけの変更
- DBだけの変更（保護対象）
- 両方の変更・コンフリクト
- 取消候補
- 警告・整合性違反

### 10.2 コンフリクト解決画面

各コンフリクトについて、最低限以下を提示する。

- 対象レコード
- 対象項目
- 前回の入力値
- 前回同期時のマスター値
- 最新の入力値
- 現在のマスター値
- 推奨処理
- ユーザーの選択肢

大量の変更がある場合は、項目単位・レコード単位でフィルタリングできることが望ましい。

### 10.3 マスター履歴画面

マスターレコード単位で変更履歴を参照できるようにする。

- 変更日時
- 変更前後の値
- 入力元・変更者
- 変更理由
- 関連コミット

### 10.4 CSV出力画面

出力前に追加・削除・変更を確認し、出力後は履歴を参照できるようにする。

## 11. 整合性・安全性

### 11.1 トランザクション

関連するマスターの更新、変更履歴、同期状態の確定を、原則として同一トランザクションで処理する。

### 11.2 同時更新

差分プレビュー時点とコミット時点の間にマスターが変更された場合は、差分を再計算するか、バージョン不一致として処理を中断する。

古いプレビューに基づいて変更を上書きしてはならない。

### 11.3 冪等性

同じ入力バッチを繰り返し処理しても、重複登録や不要な変更が発生しないことを目標とする。

### 11.4 整合性検証

共通の制約検証に加え、業務固有の制約をプラグインとして登録できるようにする。

例：

- 外部キー整合性
- 一意制約
- 著者順序
- 登録区分と料金の整合性
- 取消状態と関連レコードの整合性

### 11.5 セキュリティ

個人情報を含むデータを扱うため、以下を考慮する。

- 操作権限
- 機密情報を含む履歴へのアクセス制御
- バックアップ・出力ファイルの保護
- 履歴・スナップショットの保存期間
- CSV Formula Injection対策
- 操作ログの改ざん防止

## 12. 大会管理システムへの適用

### 12.1 入力アダプター

初期対象は以下とする。

- 講演申込フォーム
- 参加登録データ
- その他の外部CSV
- マスターの手動編集

### 12.2 マスター

初期対象は以下とする。

- 人・メール
- 講演
- 著者
- 参加登録

既存のマスターDBの構造を可能な限り維持する。

### 12.3 名寄せ

既存の人IDによる紐付け・名寄せ処理を利用しながら、入力元レコードとの対応関係を汎用管理機構へ移す。

### 12.4 入力マージ

既存の `_form_base` を利用した3者マージを、汎用エンジンへ段階的に移行する。

移行時には、既存のフォーム基準値だけでなく、同期時点のマスター基準値が存在するかを確認する。

過去のマスター基準値を正確に復元できない場合、現在のDB値を過去の基準値として無条件に登録しない。

初回移行時の安全な基準設定手順を別途設ける。

### 12.5 CSV出力

既存のCSV出力処理に、以下を追加する。

- 出力定義の識別
- 前回出力との差分
- 出力実行履歴
- 過去のCSVの参照

既存のCSV形式は、外部ツールとの互換性を維持する。

## 13. 実装段階

### Phase 1：Versioning / Diff / Merge

## 14. 受け入れテスト

最低限、以下のシナリオを検証する。

1. 同じCSVを再取り込みしても不要な変更が発生しない。
2. DBだけを修正した場合、その変更が保持される。
3. 入力元だけを変更した場合、更新候補として検出される。
4. 入力元とDBの双方が異なる変更を行った場合、競合が検出される。
5. 名寄せ後のマスター変更とフォーム変更の競合を検出できる。
6. 前回入力値と前回マスター値が異なる場合でも、変更を正しく判定する。
7. 人手で確定した値が、再取り込みで無断で上書きされない。
8. 別入力系統から同じマスターを更新する場合に競合を検出できる。
9. 手動追加したレコードが、入力元に存在しないことを理由に削除されない。
10. 複数のマスターをまたぐ更新で整合性が維持される。
11. 古いプレビューに基づく更新が防止される。
12. 同じ入力バッチを再処理しても重複しない。
13. CSV出力時に前回出力との差分が表示される。
14. CSV出力履歴が保存され、過去の内容を参照できる。
15. 出力プレビューだけでは出力履歴の基準が変更されない。
16. 過去の更新と値の採用元を追跡できる。

## 16. 非目標

初期バージョンでは以下を目標としない。

- Gitそのものの完全な再実装
- 任意のSQL操作に対する自動マージ
- 分散データベースの実装
- すべての名寄せ判断の完全自動化
- あらゆるDBスキーマの無設定での自動統合
- 外部CSVへの双方向同期
- 複数ユーザーによる分散ブランチ運用

まず、単一DB・複数入力元・複数マスターに対する安全なデータ統合を実現する。

## 17. 最終的な設計方針

本フレームワークは、以下の原則に基づく。

**原則1：入力元の原データとマスターの正本は分離する。**

**原則2：入力元とマスターの双方について、同期の基準状態を保持する。**

**原則3：変更の検出と、値を採用する判断を分離する。**

**原則4：競合する変更を暗黙に上書きしない。**

**原則5：名寄せ・統合の結果と、その根拠を追跡可能にする。**

**原則6：入力・出力・マスター更新の履歴を残す。**

**原則7：共通コアは業務固有のマスター構造に依存しない。**

**原則8：大会管理システムを最初の適用事例とし、汎用性を検証する。**

この原則によって、複数の入力元と人手による編集が混在する業務環境において、追跡可能で安全なデータ統合と履歴管理を実現する。
